# Pi-Pet Virtual Pet Extension Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` (recommended) or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a persistent virtual cat pet for Pi, displayed as ASCII art via an optional HUD panel, reacting to Pi events (success/failure/intensity) and controllable via slash commands (`/pet`).

**Architecture:** A new Pi extension `pi-pet` that persists state to `~/.pi/pet-state.json`, exposes `/pet` commands, renders an ASCII cat via an overlay widget, listens to Pi lifecycle events for mood/energy/hunger changes, and occasionally notifies the user. Pure TypeScript, ESM, uses `@earendil-works/pi-coding-agent` and `@earendil-works/pi-tui` APIs, matching the existing `my-*` extension patterns.

**Tech Stack:** TypeScript, Bun, `@earendil-works/pi-coding-agent`, `@earendil-works/pi-tui`, Vitest for tests.

## Task 2: Define Pet State Model and Persistence

**Files:**
- Create: `pi-extensions/pi-pet/types.ts`
- Create: `pi-extensions/pi-pet/state.ts`
- Create: `pi-extensions/pi-pet/state.test.ts`

- [ ] **Step 2.1: Define types in `types.ts`**

```typescript
export interface PetState {
  name: string;
  species: "cat";
  stage: "baby" | "adult";
  bornAt: string; // ISO timestamp
  lastUpdatedAt: string; // ISO timestamp
  hunger: number; // 0-100, 0 = starving
  mood: number; // 0-100, 0 = depressed
  energy: number; // 0-100, 0 = exhausted
}

export type PetEventImpact = {
  hunger?: number;
  mood?: number;
  energy?: number;
};

export type EventMagnitude = "positive-small" | "positive-large" | "negative-small" | "negative-large";
```

- [ ] **Step 2.2: Implement `PetStateManager` in `state.ts`**

Responsibilities:
- Load `~/.pi/pet-state.json` (create default if missing)
- Save state atomically
- Apply decay based on elapsed real time (offline included), clamped to `[0, 100]`
- Apply event impacts, clamped to `[0, 100]`
- Provide feed/play/sleep commands with cooldowns/limits
- Provide `getState(): PetState`

Default initial state:

```typescript
{
  name: "Mochi",
  species: "cat",
  stage: "baby",
  bornAt: now.toISOString(),
  lastUpdatedAt: now.toISOString(),
  hunger: 80,
  mood: 80,
  energy: 80,
}
```

Decay rules (configurable constants):
- Hunger increases by 2 per hour
- Mood decreases by 1 per hour
- Energy decreases by 1.5 per hour

When applying decay after elapsed time `t` hours:
- `hunger = clamp(hunger + 2*t)`
- `mood = clamp(mood - 1*t)`
- `energy = clamp(energy - 1.5*t)`

Feed/play/sleep rules:
- `feed(amount = 30)`: hunger = clamp(hunger - amount), energy = clamp(energy - 2)
- `play(amount = 20)`: mood = clamp(mood + amount), energy = clamp(energy - 10), hunger = clamp(hunger + 5)
- `sleep(amount = 40)`: energy = clamp(energy + amount), hunger = clamp(hunger + 5)

- [ ] **Step 2.3: Write tests in `state.test.ts`**

Cover:
- Default creation
- Decay over elapsed time
- Clamp bounds
- Feed/play/sleep effects
- Persistence round-trip via temp file

Expected: all tests pass with 100% coverage on `state.ts`.

- [ ] **Step 3.2: Create `classifyEvent(eventName: string, payload?: unknown): EventMagnitude | null`**

Maps Pi lifecycle/tool events to magnitude:
- `tool_result` with `test` success → `positive-small`
- `tool_result` with `build`/`deploy` success → `positive-large`
- `tool_result` with test failure/lint failure → `negative-small`
- `tool_result` with build failure → `negative-large`
- `git_push` success → `positive-small`
- `agent_error` / `tool_error` → `negative-small`

Keep the classification extensible; return `null` for unmapped events.

## Task 7: Wire Up Lifecycle Event Listeners

**Files:**
- Modify: `pi-extensions/pi-pet/index.ts`

- [ ] **Step 7.1: Listen to Pi events**

Register handlers in extension default export:
- `pi.on("session_start", ...)` — load state, apply offline decay, maybe show notice if pet missed user
- `pi.on("turn_end", ...)` — classify tool results from the turn, apply impacts, save, refresh overlay if open, trigger notice if thresholds crossed
- `pi.on("turn_start", ...)` — track last active timestamp for work-intensity decay

- [ ] **Step 7.2: Avoid double-counting**

Only apply event impacts once per turn. Aggregate multiple tool results in a single turn: take the most impactful magnitude or sum impacts (document the chosen rule).
